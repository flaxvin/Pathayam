Documentation

The specification came first

Eleven documents settled the design before the code existed, and they were kept as written rather than edited to match what got built. What the build then decided — including where implementing a rule taught us something the rule did not say — is recorded separately.

Getting started

Running it

Everything runs through Docker Compose and Node is not needed on the host. The seed builds a demo household that already contains a cash overspend, a credit overspend and a card payment, so the screens show real behaviour instead of an empty grid.

The dev profile sets a login bypass that exists only in the development image. It refuses to start anywhere production-shaped — a public hostname, real Google credentials, or NODE_ENV=production.

For a real deployment you need a domain, a Google OAuth client, and somewhere to run one container. The database is a single SQLite file on a volume; back that up and you have backed up everything. 

# clone, configure, seed
cp .env.example .env
docker compose --profile seed up seed

# development, auth bypass on
docker compose --profile dev up

# tests and typecheck
docker compose --profile test up test

# production
docker compose up -d

The invariant

What must stay true

One identity underpins the whole engine, and it is asserted after every scenario in the test suite. If a change breaks it, the change is wrong — including when the change looked like a bug fix.

It has earned its keep. It caught an uncategorised card charge that put the books out by exactly its own amount, which is the ordinary state of every imported card row between landing and being reviewed. It also caught a caching layer that disagreed with the ledger it was summarising.

Σ budget-account balances
  = Σ category balances
  + Ready to Assign
  + held for next month
  + Σ future assignments
  − unfunded credit absorbed

Conventions

Two rules the documentation follows

Verified

Worked examples are tests

Every ₹ figure in the design documents is asserted somewhere in the suite. A number in prose that nothing checks is a number that drifts, and documentation that has drifted is worse than none.

Checked

The API reference is tested against the router

A test reads the route table and the router and compares them in both directions, so a new route cannot ship undocumented and the reference cannot describe something that does not exist.

Fictional

No real financial data, anywhere

Every household, account, card and figure in the repository is invented, including in the sample statement PDFs. Real statements are locked behind a PAN, and neither those nor what they open belong in a repository.
